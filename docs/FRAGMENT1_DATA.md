## Why this matters for matching

A declaration whose size disagrees with the symbol's real extent is the usual
cause of a wrong-width or wrong-signedness load — `lh` where the target has
`lhu`, or a scalar where the asm indexes an array. Several of the size
disagreements below were hit the hard way while matching:

- `D_812346E0` is declared as a scalar in one file but indexed as a
  three-pointer array by `func_81209078` and `func_812070A0`.
- `D_812346EC` is six bytes — three `s16` — not the `s32` its neighbour
  `D_812346F2` is declared as.
- The twelve palettes at `D_8120E300`–`D_8120E460` are read with `lhu`, so they
  are `u16`; they were declared `s16` until `func_812011D0` was decoded.

Rows flagged ⚠ have a declaration that disagrees with the measured extent. That
is not automatically a bug — a symbol may legitimately be the head of a larger
region, and splat names every referenced address — but each one is worth
checking before trusting the declared type in new code.

Note that the last symbol in each `.data` file shows size `0x0`: its extent runs
to the end of the segment, which is set by the yaml rather than by a following
symbol.
