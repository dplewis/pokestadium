# Matching functions

How to turn a `#pragma GLOBAL_ASM` back into C that IDO 7.1 compiles to
byte-identical code.

The compiler is IDO 7.1 at `-O2` (see `OPTFLAGS` in the Makefile; a few objects
override it). Matching is mostly a search over *source-level* choices —
statement order, how many locals, what type each local is — because the
instruction selection is usually right on the first try and the schedule and
register allocation are what drift.

## Setup

Prerequisites beyond the README, for macOS:

- Binutils come from MacPorts, so the Makefile needs
  `MIPS_BINUTILS_PREFIX := mips-elf-` rather than `mips-linux-gnu-`.
- `CC_CHECK` is clang here, which is stricter than the README's gcc, so it needs
  extra `-Wno-*` flags to get through the existing sources.
- `tools/asm-processor/asm_processor.py` raises on symbols defined twice; that
  check is disabled locally.

asm-differ needs packages the project's `requirements.txt` does not install:

```bash
.venv/bin/python3 -m pip install ansiwrap colorama watchdog python-Levenshtein
```

Run it with the venv interpreter, and in ROM mode:

```bash
.venv/bin/python3 ./diff.py func_81207494
```

Object mode (`-o`) currently asserts on `R_MIPS_PC16` relocations, which any
object containing a jump table will have, so prefer ROM mode.

`asm/` is gitignored and regenerated by extraction. A matched function therefore
needs no `.s` deletion — replacing the `#pragma GLOBAL_ASM` line with the C is
the whole change.

## The loop

1. Read the `.s` and work out the semantics. Identify the IDO idioms (below)
   before trying to write anything.
2. Write a first candidate. Aim for correct *instructions*; ignore scheduling.
3. `make -j8`, then `.venv/bin/python3 ./diff.py <func>`.
4. Once the instruction stream matches and only registers differ, switch to
   `./tools/score_func.py <func>` and sweep variants.

`tools/m2ctx.py <file.c>` writes `ctx.c` for feeding a function to mips_to_c.

### Scoring

`./tools/score_func.py <func>` compares the built ROM against the expected words
recorded in the function's `.s` file and prints the instruction count and an
edit count:

```
$ ./tools/score_func.py func_81203C58
LENGTH MISMATCH: 131 instrs, expected 118 (+13)
109/118 instructions differ

$ ./tools/score_func.py func_81203C58 -v      # show the aligned differences
```

It reads the built function straight out of the ROM at the offset the `.s`
records, walking to the `jr $ra` and its delay slot. It deliberately does *not*
disassemble the ELF by address: fragments are overlays that share vaddr space,
so several sections can live at the same vaddr and `objdump --start-address`
will happily land in the wrong one.

The two streams are aligned with `difflib` before counting, so an inserted or
deleted instruction costs one edit instead of cascading through the rest of the
function.

**Know what it cannot tell you.** It compares whole 32-bit words, so a single
wrong register scores exactly like a wrong opcode. Once the instruction stream
is right and only allocation differs, most of the function counts as
"differing", and the number stops discriminating between candidates. The symptom
is a **flat sweep**: several genuinely different candidates all scoring
identically. That is not a sign that the axis you are varying does nothing — it
is a sign the metric has saturated. Switch back to `diff.py`, which marks
register-only differences as `r` and lets you see that the stream is actually
correct.

Two numbers stay meaningful throughout, and are worth watching directly:

- **Instruction count.** Must match exactly before anything else matters.
- **Frame size**, the `addiu $sp, $sp, -N` in the prologue. It is a direct
  readout of how many values got spilled, which is the clearest proxy for
  whether your local variables match the original's.

## Reading IDO idioms

Float conversions are the ones worth memorizing, since they are verbose and look
like noise until recognized:

| Asm | Means |
|---|---|
| `cvt.s.w` | `(f32)` of a signed int |
| `bgez` over an `add.s` of `0x4F800000` | `(f32)` of an **unsigned** int (adds 2^32 when the top bit is set) |
| `trunc.w.s` | `(s32)` of a float |
| `cfc1`/`ctc1` + `andi 0x78` + a `0x4F000000` subtract | `(u32)` of a float |

So a `trunc.w.s` immediately followed by `mfc1`, `mtc1`, `cvt.s.w` is a float →
`s32` → float round trip, which means the source has an intermediate `s32`
variable or cast that you must reproduce.

Other things that read as structure rather than noise:

- `andi reg, reg, 0xFFFF` on an incoming argument means a `u16` parameter.
- Dead `sw a0, 0(sp)` / `sw a1, 4(sp)` stores to the argument home area, never
  reloaded, also come from narrow (`u16`) parameters. They are a signal that the
  parameter types are right — if your candidate loses them, you changed
  something.
- Loads get hoisted aggressively into float latency slots, so the position of an
  `lw` says much less about source order than the position of the `sw` that
  consumes it.

## Loops and induction variables

IDO strength-reduces loops hard, and the shape it produces is a direct readout
of *where the loop variable appears in the source*. This is worth reading off
the asm before writing any C, because it is not something you can fix later by
shuffling registers.

Compare two ways of writing the same fill:

```c
for (y = 0; y < 30; y++) {            /* p bumped: one pointer, counter by 1 */
    for (x = 0; x < 30; x++) { p[x] = v; }
    p += 0x140;
}

for (y = 0; y < 30; y++) {            /* y in the index: counter by 0x140,   */
    for (x = 0; x < 30; x++) {        /* limit 30*0x140, and a derived        */
        p[y * 0x140 + x] = v;         /* pointer per use site                 */
    }
}
```

The second form makes IDO fuse the counter with the address arithmetic: the
counter advances by the row stride and the loop ends at `rows * stride`. So when
the target shows a counter incrementing by something that is obviously an
address stride, and compares against a large round multiple, the loop variable
was used inside an index expression, not to bump a pointer.

Two more readings from the same family:

- A constant byte offset that stays in the **addressing displacement**
  (`sh v1, 0x1410(a2)`) means the base pointer was *not* pre-offset in the
  source. If you write `p = base + 0x1410` you get the offset folded into the
  pointer and a `0(p)` displacement instead.
- IDO's unroller peels iterations to reach an alignment and then creates its own
  induction variable for the remainder, so *two* pointers walking the same array
  with the same stride is normal and does not mean two source variables.

Where this does **not** help: source-level constant folding. Writing
`base + 0x10 + i*0x10 + 0x5F00` rather than `base + 0x5F10 + i*0x10` does not
change which subexpressions get shared -- IDO folds the constants first either
way.

## Worked example: `func_81207494`

From `src/fragments/1/fragment1_86CB0.c`, 75 instructions. Four iterations, each
isolating one variable.

**1. Semantics.** The data gave most of it away: `D_8120EB48` is a table of
`0x20000/n`, and the two rodata constants are `48000.0f` and `24000.0f`. The
float sequence decoded as u32 → f32 → s32 → f32 → divide → multiply → u32, so
the intermediate `s32` had to be explicit. First candidate:

```c
D_8122EE98 = (arg1 * 16 + arg0) << 14;
D_8120EAC8 = D_8120EAD4[arg0 * 2 + arg1];
temp = (f32)D_8120EB48[arg2];
return (temp / D_8122B0A8) * D_8122B0AC;
```

All the float math matched immediately. Everything after this was ordering.

**2. Statement order.** The target masks `arg2` first and stores `D_8122EE98`
early, in the middle of the float conversion's latency. Moving the `D_8122EE98`
assignment to the top of the function fixed the first 21 instructions exactly —
including the dead argument spills. The `D_8120EB48` load hoists above it on its
own.

**3. Store placement.** The target defers the `D_8120EAD4` load and the
`D_8120EAC8` store all the way to the end, with the store in the `jr` delay
slot. That only happens if the assignment comes *after* the return value is
computed, which means it cannot be written as `return expr;` — the result needs
to land in a variable first. With that, every instruction matched.

**4. Register pressure.** 28 of 75 words still differed, but every single
remaining register was off by exactly `+1`:

```
  812074FC  expect 440A5000 (mfc1 t2)   got 440B5000 (mfc1 t3)
  8120750C  expect 00076880 (sll  t5)   got 00077080 (sll  t6)
  8120751C  expect 3C188121 (lui  t8)   got 3C198121 (lui  t9)
```

A *constant* offset across the whole function is the signature of one extra
local, not of bad codegen. The candidate had three (`v`, `temp`, `ret`) where
the original had two — reusing one variable for both the loaded value and the
final result dropped the pressure by one and matched exactly:

```c
u32 func_81207494(u16 arg0, u16 arg1, u16 arg2) {
    u32 temp;
    s32 temp2;

    D_8122EE98 = (arg1 * 16 + arg0) << 14;
    temp = D_8120EB48[arg2];
    temp2 = (f32)temp;
    temp = (temp2 / D_8122B0A8) * D_8122B0AC;
    D_8120EAC8 = D_8120EAD4[arg0 * 2 + arg1];
    return temp;
}
```

## Rules of thumb

- Get the instructions right first and ignore the schedule; the schedule
  usually falls out once the source order is right.
- Reordering whole statements is the highest-yield knob. IDO fills float latency
  with whatever integer work is available, so *which* statement is adjacent in
  source determines what lands in those slots.
- A store that appears in the delay slot, or unusually late, came after the
  return value in source.
- When only register *numbers* differ, and by a constant offset, count your
  locals. Fewer is usually right.
- Where the loop variable appears -- bumping a pointer vs. inside an index
  expression -- decides the induction variables IDO creates. Read that off the
  asm first; no amount of later tweaking will change it.
- Watch the frame size. It is the cheapest signal for "too many locals", and it
  moves in whole steps as variables spill.
- Do not chase register allocation until the instruction stream matches — it is
  downstream of everything else.
- If a sweep comes back flat, stop sweeping. Either the metric has saturated or
  the axis is irrelevant; either way another build of the same shape will not
  tell you anything new.
- Leave an unfinished function the way the repo already does it: the best
  candidate under `#ifdef NON_MATCHING`, the `#pragma GLOBAL_ASM` in the
  `#else`. The ROM keeps matching and the work is not lost.

## "It matches on decomp.me but not in the project"

Almost always a **context** difference, not a codegen mystery. decomp.me is
given one flattened file in which everything the function touches is already
declared. The project is not: a callee whose header you forgot to include is
implicitly declared, and IDO then assumes it returns `int` and applies default
argument promotions. That changes register allocation around the call while
leaving the instruction stream intact.

The signature of this failure is distinctive. `diff.py` shows **no structural
differences at all** -- every line is marked `r` (register) or `s` (stack slot),
often as a clean swap of two registers and their two spill slots:

```
48cd8:  lw   t0,0x64(sp)      r   48cd8:  lw   a3,0x64(sp)
48dec:  sw   a3,0x4c(sp)      s   48dec:  sw   a3,0x64(sp)
48df4:  sw   t0,0x64(sp)      s   48df4:  sw   t0,0x4c(sp)
```

Do not go looking for a source permutation. Ask the compiler instead:

```bash
touch src/<file>.c && make build/src/<file>.o 2>&1 | grep "Warning 835"
```

IDO's Warning 835 -- "No prototype for the call to an anonymous function" --
names every call it could not see a declaration for. Add the headers that
declare them and rebuild. `func_80048060` in `48C60.c` matched on decomp.me and
failed in the project for exactly this reason; it was missing `4B940.h`,
`4F410.h` and `51740.h`, and adding those three includes matched it outright
with no change to the C.

Worth grepping for proactively: a clean build of a file you are working in
should have zero Warning 835 for functions you call. The host `CC_CHECK` pass
reports the same thing as `-Wimplicit-function-declaration`, which is easier to
spot in the build log.

## Jump tables and rodata migration

A function containing a `switch` large enough for IDO to build a jump table
cannot simply be turned into C. Check before you start:

```bash
grep -c 'jlabel\|jtbl' asm/us/nonmatchings/<path>/<func>.s
```

A non-zero count means the function is blocked on the rodata layout, not on
matching. Attempting it anyway gets you to a link error, not a diff:

```
mips-elf-ld: (.rodata+0x8c): undefined reference to `.L81201324'
```

The jump table lives in a generated `.rodata` blob (for fragment 1, in
`fragment1_rodata_AA6D0.rodata.s`) and refers to labels *inside* the function's
asm. Replace the `#pragma GLOBAL_ASM` with C and those labels stop existing,
while the table still references them.

### How migration is meant to work

The yaml distinguishes two rodata segment types by a leading dot:

```yaml
- [0xAA6D0,  rodata, fragments/1/fragment1_rodata_AA6D0]   # standalone .s
- [0xAAA30, .rodata, fragments/1/fragment1_86CB0]          # migrated into the C file
```

When a range is migrated, splat writes each rodata symbol into the `.s` of the
function that references it, as a `.late_rodata` section that `asm-processor`
places. `fragment1_86CB0` already does this successfully -- see the top of
`func_8120806C.s` for what a migrated jump table looks like.

### Why it is not a one-line yaml change

Migrating `0xAA6E4` onward into `fragments/1/fragment1_7F9A0` was tried and
**does not match**. Splat did the right thing -- `jtbl_8122ADB8` moved into
`func_812011D0.s` correctly -- but the ROM came out wrong for two reasons:

1. **Order inverts.** IDO emits `.rodata` before `.late_rodata`. Jump tables are
   late_rodata, so they sort *after* plain rodata in the same object. The four
   floats at the end of that blob ended up ahead of the tables -- `first_diff.py`
   showed a float landing at `0xAA8D8` where a table entry belongs. The original
   ROM has all the tables first and the floats last.
2. **Not everything can migrate.** `D_8122AD50` sits at the front of the range
   and is referenced from already-matching C, so it has no `.s` to migrate into.
   Two further tables silently failed to migrate, leaving a 0xC-byte fill gap.

Migrated rodata lands in the C object's single `.rodata` section and is placed as
one contiguous unit, so a file's entire rodata has to be contiguous in the ROM
*and* in compiler-emission order. For `fragment1_7F9A0` neither currently holds.
Making it work means moving `D_8122AD50` into the C file as real data, settling
whether those trailing floats are `.rodata` or `.late_rodata`, and confirming the
whole range can be emitted in ROM order -- which function-order emission may not
be able to do, since `func_81202210`'s constants would land between two tables
rather than after them.

### If you do attempt it

Change the yaml and rebuild with **every function still behind its pragma**
first. That isolates the layout change from any decompilation, so a checksum
failure can only mean the migration itself is wrong. Only once the ROM still
matches should a function be moved to C.

Re-running splat on its own is reproducible and safe, and does not require the
destructive `make extract` (which also wipes and re-extracts `assets/`):

```bash
cat yamls/us/header.yaml yamls/us/rom.yaml > pokestadium-us.yaml
.venv/bin/python3 -m splat split pokestadium-us.yaml
```

Reverting the yaml and re-running that restores a matching build, so the
experiment is cheap to back out of.

Splat also emits unprompted advisories worth reading, of the form
"Rodata segment X may belong to the text segment Y". Those are further latent
migrations it has already spotted.

## decomp-permuter

Manual search works while there is a structural hypothesis to test -- a statement
order, a missing local, a type. Once the instruction stream matches and only
register allocation is left, the remaining search space is source permutations
that a human has no good intuition for. That is what `decomp-permuter` is for.

It lives at `../decomp-permuter` (a sibling of this repo), and uses this repo's
`tools/permuter_settings.toml`, which is already configured for `ido7.1`.

### Setup on macOS

The tool assumes a Linux-ish toolchain, so three things need doing beyond the
clone. All three are one-time.

```bash
git clone https://github.com/simonlindholm/decomp-permuter.git   # as a sibling of this repo
.venv/bin/python3 -m pip install pynacl toml Levenshtein          # into THIS repo's venv
```

1. **A GNU preprocessor.** `import.py` hardcodes
   `cpp_cmd = homebrew_gcc_cpp() if is_macos else "cpp"`, which scans
   `/usr/local/bin` and `/opt/homebrew/bin` for a `cpp-*` binary. Apple's clang
   `cpp` cannot substitute -- the permuter passes `-fdirectives-only`, which is
   GCC-only. Fix with `brew install gcc` (provides `cpp-16`).
2. **`gmake`.** Also hardcoded for macOS (`make_cmd = "gmake" if is_macos`).
   Homebrew's `make` formula provides it.
3. **An objdump under a name it recognises.** `src/objdump.py` looks only for
   `mips-linux-gnu-objdump`, `mips64-linux-gnu-objdump` or
   `mips64-elf-objdump`, so MacPorts' `mips-elf-objdump` is invisible to it.
   Symlink rather than patching the checkout, so it survives updates:

   ```bash
   ln -sf /opt/local/bin/mips-elf-objdump ~/bin/mips64-elf-objdump
   ```

Run the permuter with `~/bin` on PATH and using this repo's venv interpreter,
since that is where the Python dependencies were installed.

### Importing a function

Because in-progress functions live under `#ifdef NON_MATCHING`, pass
`NON_MATCHING=1` so the candidate C is what gets imported rather than the
`GLOBAL_ASM` stub. Give the `.s` path explicitly:

```bash
cd ../decomp-permuter
../pokestadium/.venv/bin/python3 ./import.py \
    ../pokestadium/src/fragments/1/fragment1_7F9A0.c \
    ../pokestadium/asm/us/nonmatchings/fragments/1/fragment1_7F9A0/func_812016DC.s \
    NON_MATCHING=1
```

It reads the compiler command out of the Makefile itself, so the IDO invocation
and the `mips-elf-as` assembler are picked up automatically.

### Running

```bash
PATH="$HOME/bin:$PATH" ../pokestadium/.venv/bin/python3 \
    ./permuter.py --debug nonmatchings/func_812016DC        # score the base only
PATH="$HOME/bin:$PATH" ../pokestadium/.venv/bin/python3 \
    ./permuter.py -j8 --best-only --stop-on-zero nonmatchings/func_812016DC
```

`--debug` scores the base and exits, which is the fastest way to confirm the
import is sound. Improvements are written to `nonmatchings/<func>/output-<score>-N/`.

The status line rewrites itself with carriage returns, so the log is unreadable
with plain `tail`. To get the actual progress:

```bash
tr '\r' '\n' < run.log | grep -oE "score = [0-9]+" | awk '{print $3}' | sort -n | head
```

### Reading the score

`--debug` prints the penalty breakdown, and it is a far better diagnostic than
my `score_func.py`, which cannot tell a wrong register from a wrong opcode:

```
Register Differences:          51  (5)
Insertions:                     3  (100)
Deletions:                      3  (100)
[func_812016DC] base score = 855
```

Insertions and deletions are weighted 100 and registers only 5, so the score is
dominated by whether the instruction stream is right. A score that is a clean
multiple of 5 means the stream matches and only allocation is left.

Note that permuter output is not directly committable -- it reaches low scores
with `do { ... goto label; } while (0)` wrappers, empty `if (x) {}` blocks and
joined lines. Those do genuinely change IDO's codegen, but once a match is found
the result has to be worked back into something readable that still compiles to
the same thing.
